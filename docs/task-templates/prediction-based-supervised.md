# Task Template — Prediction-based (Supervised Learning)

Template สำหรับโจทย์ประเภททำนายผลแบบ supervised ที่ **ประเมินผลบน hidden test set** ใช้ซ้ำได้กับหลายวิชา
เอกสารนี้เป็น spec ระดับแพลตฟอร์ม — โจทย์จริงของแต่ละวิชาอยู่ใน [`docs/competitions/`](../competitions/)

แบ่งเป็น 2 variant ที่ใช้กลไกเดียวกันเกือบทั้งหมด ต่างกันแค่รูปแบบ artifact และ interface

| Variant | นิสิตส่ง | รันบน | ใช้กับ |
|---|---|---|---|
| **`classical-ml`** | scikit-learn model (pickle) + preprocessing script | CPU lane | วิชา ML พื้นฐาน — tabular data, feature engineering |
| **`deep-learning`** | PyTorch `state_dict` (.pt) + model/dataset script | GPU lane (RTX 3090) | วิชา DL — image, text, signal |

**ขอบเขตตอนนี้: supervised learning เท่านั้น** (classification เป็นหลัก) — unsupervised / self-supervised / generative ยังไม่รองรับ

## 1. การแบ่งข้อมูลและสิทธิ์เข้าถึง

ข้อมูลทั้งหมดเก็บที่ **GPU server ในมหาวิทยาลัย** ไม่อัพขึ้น cloud

| Split | นิสิตดาวน์โหลดได้ | มี label | ใช้ทำอะไร |
|---|---|---|---|
| `train` | ✅ | ✅ | นิสิตเทรนเอง |
| `val` | ✅ | ✅ | นิสิตจูนเอง / แพลตฟอร์มใช้ตรวจ dry run |
| `test_public` | ❌ | เก็บที่ server | คะแนนบน public leaderboard ระหว่างเทอม |
| `test_private` | ❌ | เก็บที่ server | **ตัดสินอันดับและเกรดจริง** เปิดตอนปิดเทอม |

**การดาวน์โหลด** — signed URL ต่อทีม หมดอายุใน 24 ชม. + log ว่าใครดาวน์โหลดเมื่อไร

**สัดส่วนการแบ่ง: ผู้สอนของแต่ละวิชากำหนดเอง** ผ่าน `TaskSpec` เพราะขึ้นกับขนาดและลักษณะของชุดข้อมูลที่ใช้

```yaml
split:
  train: 0.60
  val: 0.15
  test_public: 0.10
  test_private: 0.15
  stratify_by: label      # หรือชื่อคอลัมน์อื่น / null
  group_by: null          # ถ้ามีหลายแถวต่อ 1 subject ต้องแบ่งตาม subject ไม่ใช่ตามแถว
  seed: 42
```

**ข้อบังคับที่แพลตฟอร์มตรวจให้ ไม่ว่าผู้สอนจะตั้งสัดส่วนเท่าไร**

- `test_public` กับ `test_private` ต้อง stratify เหมือนกันและมาจาก distribution เดียวกัน มิฉะนั้นอันดับจะสลับด้วยเหตุผลที่ไม่เกี่ยวกับฝีมือ
- `test_private` ควร **ไม่เล็กกว่า** `test_public` — public ต้องการแค่สัญญาณพอให้รู้ว่าเดินถูกทาง แต่ private ต้องแม่นพอใช้ตัดสินเกรด
- ถ้ามีหลายแถวต่อหนึ่ง subject/ผู้ป่วย/ผู้ใช้ ต้องตั้ง `group_by` ไม่งั้นเกิด group leakage ข้าม split (ระบบเตือนถ้าเจอค่าซ้ำข้าม split)
- ระบบเตือนตอนสร้าง competition ถ้า `test_private` เล็กเกินไปเทียบกับความละเอียดที่ต้องการ (ดูตารางล่าง)

**ตัวช่วยเลือกขนาด `test_private`** — จำนวนตัวอย่างที่ต้องมีเพื่อให้ CI แคบพอ (ที่ระดับคะแนนราว 85%)

| ต้องการความละเอียด (ครึ่งความกว้าง CI) | จำนวนตัวอย่างที่ต้องมี |
|---|---|
| ±5 จุด | ~200 |
| ±3 จุด | ~550 |
| ±2 จุด | ~1,200 |
| ±1 จุด | ~4,900 |

> **ถ้าคะแนนหลักคือ recall/precision ของคลาสใดคลาสหนึ่ง ให้นับเฉพาะตัวอย่างของคลาสนั้น**
> เช่นงาน screening ที่ positive มี 10% ถ้าอยากได้ ±3 จุดบน recall ต้องมี positive ~550 ตัว → `test_private` ต้องมีประมาณ **5,500 แถว**
> ข้อนี้มักเป็นตัวกำหนดขนาดจริง ไม่ใช่ accuracy

ถ้าชุดข้อมูลทั้งหมดเล็กจนแบ่งแล้ว `test_private` ไม่ถึงเกณฑ์ ทางเลือกคือ: ลด `val` (ให้นิสิตทำ k-fold บน train แทน) → ลด `test_public` → หรือยอมรับว่าจะแยกทีมได้แค่หยาบๆ แล้วให้เกรดแบบ threshold กว้างๆ ไปเลย

### 1.1 ทำไม test ต้องแยกเป็น public / private

เหตุผลไม่ใช่เรื่องกันนิสิตเห็นข้อมูล (นิสิตไม่เห็นทั้งสองก้อนอยู่แล้ว) แต่เป็นเรื่อง **การเลือกตัวที่ดีที่สุดจากการวัดหลายครั้ง**

คะแนนที่วัดได้ = ฝีมือจริง + noise จากการที่ test set มีขนาดจำกัด
ถ้า test set มี 1,000 ตัวอย่างและโมเดลมีฝีมือจริง 85% ค่าที่วัดได้จะแกว่ง SE ≈ 1.13 จุด
ทีมที่ส่ง 50 ครั้งแล้วเลือกครั้งที่ดีที่สุด จึงไม่ได้ "ค่าจริง" แต่ได้ **ค่าสูงสุดของการสุ่ม 50 ครั้ง**

| ทีม | ฝีมือจริง | จำนวนครั้งที่ส่ง | ถ้ามี test ก้อนเดียว (เลือกดีที่สุด) | ถ้ามี private (วัดครั้งเดียว) |
|---|---|---|---|---|
| A | 85.0% | 50 | 85.0 + 1.13 × 2.25 = **87.5** | **85.0** ± 1.1 |
| C | 86.0% | 3 | 86.0 + 1.13 × 0.85 = **87.0** | **86.0** ± 1.1 |
| | | | A ชนะ — **ทั้งที่ฝีมือด้อยกว่า** | C ชนะ ~73% ของกรณี |

`2.25` และ `0.85` คือค่าคาดหวังของค่าสูงสุดจากการสุ่ม 50 และ 3 ครั้ง — ยิ่งส่งเยอะตัวคูณยิ่งโต
ผลคือ leaderboard วัด "ใครขยันส่ง" ปนกับ "ใครเก่ง" โดยไม่มีใครตั้งใจโกงเลย

> **ยิ่ง metric พึ่ง subgroup เล็ก ยิ่งแรง** — ถ้าคะแนนหลักเป็น recall ของ positive class ในงาน screening ที่ positive มีแค่ 10%
> recall จะคำนวณจากตัวอย่างแค่ 100 ตัว → SE = 3.6 จุด ไม่ใช่ 1.1 จุด ผลของการเลือกตัวที่ดีที่สุดจึงแรงขึ้นราว 3 เท่า

**ทำไม private ถึงแก้ได้** — กลไกมี 2 ชิ้น และขาดชิ้นใดชิ้นหนึ่งไม่ได้

1. **โชคไม่ข้ามชุดข้อมูล** — เวอร์ชันที่ "บังเอิญได้ดี" ไม่ได้เก่งขึ้น มันแค่เดาถูกในเคสก้ำกึ่งที่อยู่ใน `test_public` ก้อนนั้นโดยเฉพาะ
   พอเจอ `test_private` ที่เป็นคนละตัวอย่าง ความบังเอิญนั้นไม่ตามไปด้วย — **ฝีมือข้ามชุดข้อมูลได้ โชคข้ามไม่ได้**
2. **ทุกทีมได้วัดเท่ากัน** — ต้องจำกัดจำนวน submission ที่เอาไปรันบน private (ดู §1.2)
   ถ้าเอาทั้ง 50 ชุดของทีม A ไปรันบน private แล้วเลือกอันที่ดีที่สุด private จะพังด้วยเหตุผลเดียวกันเป๊ะ

ความต่างที่แท้จริงคือ **ลักษณะของความผิดพลาด**: ก้อนเดียว → ผิดแบบมีทิศทาง เข้าข้างคนส่งเยอะเสมอ ทำซ้ำกี่รอบก็ผิดทางเดิม
private → ผิดแบบสุ่มรอบค่าจริง ไม่เข้าข้างใคร ค่าคาดหวังตรงกับฝีมือจริง

**การแบ่งหน้าที่ระหว่างสองก้อน**

| | จับ overfit ต่อ **training data** | จับ overfit ต่อ **leaderboard เอง** (adaptive overfitting) |
|---|---|---|
| `test_public` | ✅ | ❌ — มันคือตัวที่ถูก overfit เข้าหา |
| `test_private` | ✅ | ✅ |

`test_public` ถูกออกแบบมาให้ **ถูกใช้จนเสื่อมสภาพ** นั่นคือหน้าที่ของมัน อันดับบน public leaderboard เอียงเข้าข้างทีมที่ส่งเยอะจริง
เรายอมรับข้อนี้ได้เพราะ public ไม่ได้ตัดสินเกรด

**ทำไมใช้ `val` แทน `test_public` ไม่ได้** — เพราะนิสิตถือ `val` อยู่ในมือ
1. ทีมที่เอา `val` ไปเทรนด้วยจะขึ้นอันดับ 1 ทันทีโดยโมเดลไม่ได้เก่งขึ้น → **ความซื่อสัตย์มีต้นทุน**
2. ขั้นตอนที่ถูกต้องของ ML คือจูนบน val เสร็จแล้ว **retrain บน train+val** — leaderboard บน val จะทำให้การทำถูกวิธีดูเหมือนโกง เราจะส่งสัญญาณผิดทั้งเทอม
3. นิสิตคำนวณคะแนน val เองได้อยู่แล้ว leaderboard จึงไม่ได้บอกอะไรใหม่
4. ทีมที่ overfit จะไม่รู้ตัวจนเปิด test วันสุดท้าย — สายเกินแก้ ทั้งที่ประเด็นนี้คือสิ่งที่เราอยากให้เขาเรียนรู้**ตอนที่ยังลงมือแก้ทัน**

### 1.2 กติกา Final Pick — ส่วนที่ขาดไม่ได้

private set จะทำงานได้ต่อเมื่อ **ทุกทีมได้วัดบนมันเท่ากัน**

```
ก่อนปิดรับ → ทีมเลือกเอง สูงสุด 2 submission (ตัดสินใจจากคะแนน public + วิจารณญาณตัวเอง)
ปิดรับแล้ว  → ระบบรันเฉพาะ 2 ชุดนั้นบน private → ใช้อันที่ดีกว่าเป็นคะแนนสุดท้าย
```

- **ห้ามให้ระบบเป็นคนหยิบโดยดูคะแนน private** — เท่ากับให้ทีมที่ส่งเยอะจับฉลากเยอะกว่า กลับไปเป็นปัญหาเดิม
- หัวใจไม่ได้อยู่ที่จำนวนต้องเป็น 1 แต่อยู่ที่ **เท่ากันทุกทีม** — max-of-2 ก็เบ้ขึ้นเล็กน้อย แต่เบ้เท่ากันหมด อันดับเปรียบเทียบจึงไม่บิด
- ทีมที่ไม่เลือก ระบบใช้ submission ที่คะแนน public สูงสุดเป็นค่าเริ่มต้น
- การให้ทีมเลือกเองมีคุณค่าทางการสอน: บังคับให้ตอบคำถามว่า "เวอร์ชันไหนน่าจะ generalize ดีที่สุด" ซึ่งไม่ใช่คำถามเดียวกับ "เวอร์ชันไหนคะแนน public สูงสุด"

### 1.3 สิ่งที่ยังแก้ไม่ได้

จากตัวอย่างข้างบน ยังเหลือโอกาส ~27% ที่ทีม C แพ้เพราะดวง — แก้ด้วยการแบ่ง split ไม่ได้ แก้ได้ทางเดียวคือ test set ใหญ่ขึ้น
เพราะฝีมือต่างกัน 1 จุด แต่เครื่องมือวัดหยาบ ±1.1 จุด ซึ่งรับมือด้วยสองอย่างที่ออกแบบไว้แล้ว

- **95% CI บน leaderboard** (§6, §7) — บอกตรงๆ ว่าช่องว่าง 1 จุดนั้นวัดไม่ได้จริง แทนที่จะแกล้งทำเป็นว่าอันดับ 1 กับ 2 ต่างกันชัด
- **ให้เกรดแบบ threshold ไม่ใช่ตามอันดับ** ([README §5.3](../../README.md#53-การแปลงคะแนนเป็นเกรด)) — การพลิกอันดับที่มีโอกาส 27% จะไม่กระทบเกรดใคร

สรุป: private split แก้ **ความลำเอียงเชิงระบบ** (แก้ได้และต้องแก้) · CI กับ threshold grading รับมือ **ความไม่แน่นอนที่เหลือ** (แก้ไม่ได้ แต่บอกความจริงกับนิสิตได้)

## 2. สิ่งที่นิสิตส่ง

### 2.1 Variant `classical-ml`

```
submission.zip
├── model.pkl           # scikit-learn estimator (fitted) — joblib หรือ pickle
├── preprocess.py       # feature engineering (ดู §3.1)
├── requirements.txt    # optional — จำกัดตาม whitelist
└── SOURCES.md          # อ้างอิงที่มาของไอเดีย/โค้ด (บังคับตอนส่ง final)
```

ขนาดปกติ < 10 MB → เก็บถาวรได้ทุก submission ไม่เป็นภาระ server

### 2.2 Variant `deep-learning`

```
submission.zip
├── model.pt            # state_dict เท่านั้น (ไม่ใช่ทั้ง nn.Module)
├── model.py            # นิยามสถาปัตยกรรม (ดู §3.2)
├── dataset.py          # Dataset + DataLoader (ดู §3.2)
├── config.json         # hyperparameter ที่ต้องใช้สร้างโมเดล
├── requirements.txt
└── SOURCES.md
```

> **หมายเหตุ: ให้ส่ง `state_dict` ไม่ใช่ทั้งโมเดล**
> ที่อาจารย์ร่างไว้คือ "upload model เป็น .pt file" ซึ่งถ้าเป็น `torch.save(model)` ทั้งก้อน ตอนโหลดจะต้องใช้ `torch.load(weights_only=False)`
> ที่ **unpickle = รันโค้ดที่ฝังมาในไฟล์** บนเครื่องที่เก็บ test set อยู่ (ดู §8)
> การให้ส่ง `state_dict` + `model.py` แยกกันทำให้โหลดด้วย `weights_only=True` ได้อย่างปลอดภัย
> และได้ผลพลอยได้คือสถาปัตยกรรมกลายเป็นโค้ดที่อ่านได้ ตรวจความคล้ายระหว่างทีมได้ และ rejudge ได้ในอนาคต
> — ยังเป็นไฟล์ `.pt` เหมือนเดิม เปลี่ยนแค่สิ่งที่อยู่ข้างใน

## 3. Contract ของโค้ดนิสิต

### 3.1 `classical-ml` — `preprocess.py`

```python

class Preprocessor:
    """แปลง raw dataframe → feature matrix ที่ model.pkl รับได้"""

    def fit(self, df: pd.DataFrame, y: pd.Series) -> "Preprocessor":
        """เรียนรู้พารามิเตอร์ทั้งหมด (scaler, encoder, imputer, ...) จาก train เท่านั้น"""
        ...
        return self

    def transform(self, df: pd.DataFrame) -> pd.DataFrame:
        """ต้อง deterministic และต้องไม่เรียนรู้อะไรจาก df ที่รับเข้ามา"""
        ...
```

ระบบจะเรียกตามลำดับนี้เป๊ะๆ:

```python
p = Preprocessor().fit(train_df, train_y)     # fit บน train เท่านั้น
X_test = p.transform(test_df)                  # แล้วค่อย transform test
y_prob = model.predict_proba(X_test)
```

> **ทำไมต้องมี `fit` / `transform` แยกกัน**
> ที่ร่างไว้เดิมคือ "script ที่ให้ output เป็น dataframe ของ train และ val แล้วระบบเอาไปใช้กับ test"
> ถ้าเป็นฟังก์ชันเดียวที่รับ dataframe แล้วคืน dataframe จะเกิดปัญหาที่หลีกเลี่ยงไม่ได้ 2 อย่าง
> 1. **Data leakage** — `StandardScaler().fit_transform(df)` หรือ imputer ที่ใช้ค่า mean ของ df จะไป fit บน test โดยไม่ตั้งใจ ทำให้คะแนนสูงเกินจริง
> 2. **Column mismatch** — `pd.get_dummies(test_df)` จะได้คอลัมน์ไม่ตรงกับตอน train ถ้า test ไม่มีบางหมวดหมู่ → พังหรือได้ผลมั่ว
>
> การบังคับ `fit(train)` แล้ว `transform(test)` แก้ทั้งสองข้อ และตรงกับสิ่งที่นิสิต**ควร**ทำอยู่แล้วในทางปฏิบัติ
> ถ้าทีมไหนอยากส่ง preprocessor ที่ fit ไว้แล้วมาเลย ก็ทำได้ — pickle มันมาในไฟล์ แล้วให้ `fit()` เป็น no-op

**ข้อกำหนดเพิ่ม**

- `transform` ต้อง **deterministic** — ถ้ามีการสุ่ม ต้องตรึง seed ภายใน
- คอลัมน์และ dtype ของ `transform(test_df)` ต้องตรงกับ `transform(train_df)` ทุกประการ ระบบตรวจอัตโนมัติ
- ห้ามอ่านไฟล์นอก working directory ห้ามเรียก network
- `model.pkl` ต้องมี `predict_proba` (หรือ `decision_function`) มิฉะนั้นคำนวณ ROC-AUC / PR curve ไม่ได้

## 4. การกัน Data Leakage

นอกจากบังคับ `fit`/`transform` แล้ว ระบบตรวจอัตโนมัติเพิ่ม 3 ชั้น

| การตรวจ | วิธี | ถ้าไม่ผ่าน |
|---|---|---|
| **Subset consistency** | เรียก `transform` บน test ทั้งก้อน แล้วเรียกอีกครั้งบน subset สุ่ม 30% เทียบผลของแถวเดียวกัน — ถ้าต่างกัน แปลว่า transform ใช้สถิติของ batch ที่รับเข้ามา = fit บน test | ปฏิเสธ submission พร้อมบอกว่าคอลัมน์ไหนไม่ตรง |
| **Row permutation invariance** | สลับลำดับแถวแล้ว transform ใหม่ ผลของแต่ละแถวต้องไม่เปลี่ยน | เตือน + ปฏิเสธ |
| **Schema match** | คอลัมน์/dtype ของ `transform(test)` ต้องตรงกับ `transform(train)` | ปฏิเสธ |

Subset consistency check เป็นตัวที่จับ leakage ได้จริงและถูกที่สุด — scaler/imputer/target-encoder ที่ fit บน batch จะให้ค่าต่างกันทันทีเมื่อ batch เปลี่ยน

## 5. Pipeline การประเมินผล

แยกเป็น 2 stage โดยเจตนา **โค้ดนิสิตไม่เคยอยู่ในกระบวนการเดียวกับเฉลย**

```
┌─ Stage 1: UNTRUSTED (container ของนิสิต) ────────────────┐
│  input : train (มี label), test features (ไม่มี label)   │
│  รัน   : preprocess/dataset → model → predict_proba      │
│  output: predictions.parquet (sample_id, prob_*)         │
│  network: none · non-root · read-only fs · timeout       │
└──────────────────────┬───────────────────────────────────┘
                       │ ส่งออกได้แค่ไฟล์ predictions
┌──────────────────────┴─ Stage 2: TRUSTED (ของแพลตฟอร์ม) ─┐
│  input : predictions + เฉลย test                         │
│  รัน   : คำนวณ metrics + bootstrap CI + curves           │
│  output: metrics.json, roc.json, pr.json                 │
└──────────────────────────────────────────────────────────┘
```

**ทำไมต้องแยก** — โค้ดนิสิตรันได้อิสระอยู่แล้ว (unpickle = execute) ถ้าเฉลยอยู่ในหน่วยความจำเดียวกัน การป้องกันจะขึ้นกับ sandbox อย่างเดียว
การไม่ให้เฉลยเข้าไปใน stage 1 เลย ทำให้ **ต่อให้หนีออกจาก sandbox ได้ ก็ยังไม่มีเฉลยให้อ่าน** — เป็นการป้องกันเชิงโครงสร้าง ไม่ใช่เชิงการตั้งค่า

test **features** ยังต้องเข้าไปใน stage 1 (จำเป็นต่อการทำนาย) แต่ออกไปไหนไม่ได้เพราะไม่มีเน็ต และ output ถูกจำกัดให้เป็นไฟล์ predictions ตาม schema เท่านั้น
stdout/stderr ถูกตัดที่ 1 MB และกรอง path ของระบบก่อนแสดงให้นิสิต

## 6. Metrics และ 95% Confidence Interval

### 6.1 ตัวเลขที่รายงาน

| Metric | binary | multiclass |
|---|---|---|
| Accuracy | ✅ | ✅ |
| Precision / Recall / F1 | ของ positive class | macro + weighted (ประกาศใน TaskSpec ว่าตัวไหนเป็นหลัก) |
| ROC-AUC | ✅ | macro one-vs-rest |
| PR-AUC (Average Precision) | ✅ | macro one-vs-rest |
| ROC curve / PR curve | ✅ | ต่อคลาส + micro-average |
| Confusion matrix | ✅ | ✅ |

curve เก็บเป็นจุดที่ downsample แล้ว ~200 จุดใน `metrics_json` เพื่อวาดบนหน้าผลได้โดยไม่ต้องเก็บ prediction ดิบ

### 6.2 วิธีคำนวณ CI — bootstrap

```
B = 1000 resample จาก test set แบบ stratified (สุ่มแบบมีคืนที่)
seed คงที่ต่อ competition → CI ของทุกทีมเทียบกันได้ และรันซ้ำได้ค่าเดิม
point estimate = คำนวณจาก test set เต็ม
CI            = percentile ที่ 2.5 และ 97.5 ของค่าที่ได้จาก B resample
```

**สิ่งที่ CI นี้บอกและไม่บอก** — บอกความไม่แน่นอนที่มาจาก "test set มีขนาดจำกัด" เท่านั้น
ไม่ได้บอกความไม่แน่นอนจากการเทรน (seed, initialization) เพราะเราประเมินโมเดลที่ส่งมาแล้ว 1 ตัว
ถ้าอยากได้อย่างหลังต้องให้นิสิตส่งหลาย seed ซึ่งยังไม่อยู่ใน scope

### 6.3 คะแนนหลักสำหรับ leaderboard

แพลตฟอร์มต้องการสเกลาร์ตัวเดียว ([README §5.1](../../README.md#51-metric-เป็นของแต่ละโจทย์-ไม่ใช่ของแพลตฟอร์ม)) — `TaskSpec` ต้องประกาศว่าใช้ตัวไหน

| สถานการณ์ | แนะนำ |
|---|---|
| คลาสสมดุลพอสมควร | **macro-F1** |
| คลาสไม่สมดุลมาก (positive < 10%) | **PR-AUC** — ROC-AUC จะดูดีเกินจริงเมื่อ negative เยอะมาก |
| สนใจการจัดอันดับมากกว่าการตัดสินใจ | **ROC-AUC** |

ห้ามใช้ accuracy เป็นคะแนนหลักถ้าข้อมูลไม่สมดุล (ทำนายคลาสเดียวรวดก็ได้ 90% แล้ว)
**เกณฑ์ตัดสินเสมอ**: คะแนนหลัก → ขอบล่างของ CI → metric รองที่ประกาศไว้ → เวลาที่ส่งก่อน

## 7. Leaderboard เมื่อ CI ทับกัน

พอรายงาน CI แล้วจะเห็นชัดว่าทีมที่อันดับ 1–5 มักมี CI ทับกันหมด — leaderboard จึงต้องแสดงเรื่องนี้ ไม่ใช่ซ่อนไว้

- แสดงคะแนนพร้อมแถบ CI ทุกแถว
- จัดกลุ่มทีมที่ CI ทับกับอันดับ 1 เป็น **"กลุ่มที่แยกกันไม่ได้ทางสถิติ"** แล้ว mark ไว้บนตาราง
- อันดับที่แสดงยังเรียงตาม point estimate (ต้องมีอันดับเพื่อให้เกม dynamic ทำงาน) แต่มีหมายเหตุกำกับ

> อันนี้มีคุณค่าทางการสอนโดยตรง: นิสิตจะได้เห็นเองว่าการไล่คะแนนจาก 0.912 เป็น 0.914 นั้นไม่มีความหมาย
> และการให้เกรดแบบ threshold ([README §5.3](../../README.md#53-การแปลงคะแนนเป็นเกรด)) ก็ยุติธรรมกว่าการให้เกรดตามอันดับด้วยเหตุผลนี้

## 8. ความปลอดภัย: pickle และ torch.load

**`pickle.load()` และ `torch.load(weights_only=False)` = รันโค้ดที่ผู้ส่งกำหนดได้ทั้งหมด** ไม่ใช่แค่อ่านข้อมูล
เครื่องที่รันคือเครื่องเดียวกับที่เก็บ test set และเฉลยของทุกวิชา จึงต้องถือว่า submission ทุกอันเป็นโค้ดที่ไม่น่าเชื่อถือ

| ชั้นป้องกัน | รายละเอียด |
|---|---|
| **แยก stage** | เฉลยไม่เคยเข้าไปใน process เดียวกับโค้ดนิสิต (§5) — ชั้นนี้สำคัญที่สุด |
| **Sandbox** | `--network none`, non-root, read-only rootfs, drop capabilities, pid/memory/time limit, mount เฉพาะ input ของตัวเอง |
| **`weights_only=True`** | บังคับกับ PyTorch ได้เพราะเราให้ส่ง `state_dict` (§2.2) |
| **จำกัดขนาด output** | predictions ต้องตรง schema, stdout ตัดที่ 1 MB |
| **Audit** | เก็บ hash ของทุก artifact + log ทุก run |

สำหรับ scikit-learn ยังต้องใช้ pickle เพราะเป็นรูปแบบมาตรฐาน — ทางเลือกที่ปลอดภัยกว่าคือ [`skops.io`](https://skops.readthedocs.io/)
ที่โหลดแบบ allowlist ได้ แต่รองรับ estimator ไม่ครบทุกตัว **ข้อเสนอ: เริ่มด้วย pickle ใน sandbox ตาม §5 ไปก่อน** แล้วประเมิน skops ทีหลังถ้าจำเป็น

ปัญหาที่จะเจอแน่นอนถ้าไม่ทำ: นิสิต pickle ด้วย scikit-learn 1.7 แต่ server มี 1.5 → โหลดไม่ขึ้น หรือโหลดขึ้นแต่พฤติกรรมต่าง

## 10. นโยบายเก็บ/ลบไฟล์

| Artifact | ขนาดทั่วไป | นโยบาย |
|---|---|---|
| `.py` ทุกไฟล์ | KB | **เก็บถาวร** — ใช้ตรวจความคล้าย, rejudge, ตรวจสอบย้อนหลัง |
| `model.pkl` (sklearn) | < 10 MB | **เก็บถาวร** |
| `model.pt` (torch) | 50 MB – 2 GB | **เก็บเฉพาะ best-so-far ของแต่ละทีม + submission ที่เลือกเป็น final** ที่เหลือลบทันทีหลังประเมินเสร็จ |
| predictions | MB | เก็บ 30 วัน (ใช้ debug และคำนวณ metric เพิ่มย้อนหลังได้) |
| metrics + curves | KB | เก็บถาวร |
| log | KB | เก็บ 30 วัน |

> **หมายเหตุ: อย่าลบ `.pt` ทุกอันหลังประเมิน**
> ที่อาจารย์ร่างไว้คือลบทิ้งหลังประเมินเสร็จเพื่อประหยัดพื้นที่ ซึ่งถูกต้องในแง่พื้นที่ แต่จะทำให้เสียความสามารถ 2 อย่างที่จำเป็นตอนปิดเทอม
> 1. **Rejudge ไม่ได้** — ถ้าพบบั๊กใน evaluation pipeline สัปดาห์ที่ 12 จะรันย้อนหลังใหม่ไม่ได้ ต้องให้ทุกทีมส่งใหม่หมด
> 2. **ตรวจสอบผู้ชนะไม่ได้** — ยืนยันไม่ได้ว่าคะแนนที่ประกาศมาจากโมเดลตัวไหน
>
> การเก็บแค่ "ตัวที่ดีที่สุดของแต่ละทีม + final pick" ได้ประโยชน์ทั้งสองข้อโดยใช้พื้นที่ประมาณ
> `จำนวนทีม × 2 × ขนาดโมเดล` ≈ 20 × 2 × 500 MB ≈ **20 GB** เทียบกับการเก็บทุก submission ที่จะเป็นระดับหลาย TB

**Storage quota ต่อทีม** — กำหนดเพดานไว้ (เช่น 5 GB) แล้วแสดงบนหน้าเว็บ เกินแล้วส่งไม่ได้จนกว่าจะลบเอง

## 11. ข้อจำกัดทรัพยากรและคิว

| | `classical-ml` | `deep-learning` |
|---|---|---|
| เลนคิว | CPU | GPU (RTX 3090 — ทีละงาน) |
| เวลาสูงสุดต่อ run | 10 นาที | 20 นาที |
| RAM | 8 GB | 16 GB + VRAM 20 GB |
| ขนาด submission | 50 MB | 2 GB |
| โควตาส่ง | ตามที่ผู้สอนตั้ง (เริ่มที่ 5/วัน/ทีม) | **ควรน้อยกว่า** (เช่น 3/วัน/ทีม) |

**คอขวดสำคัญ: มี GPU ใบเดียว** — งาน DL รันทีละงาน ถ้า 20 ทีมส่งพร้อมกันคืนก่อน deadline ที่ 15 นาที/งาน จะใช้เวลา 5 ชั่วโมงกว่าจะครบรอบเดียว
มาตรการ: fair-share queue (ทีมละ 1 งานพร้อมกัน วนรอบ ไม่ใช่ FIFO ล้วน) + แสดงเวลารอโดยประมาณ + ปิดรับก่อน deadline จริง 6 ชม.
วิชาที่ใช้ `classical-ml` ไม่กระทบ เพราะอยู่คนละเลน

## 12. Error handling และ Dry Run

ภาระ support ที่ใหญ่ที่สุดของโจทย์แบบนี้คือ "ส่งแล้วพัง แต่ไม่รู้ว่าพังเพราะอะไร" — ต้องออกแบบให้ fail เร็วและอ่านรู้เรื่อง

**ตรวจตั้งแต่ตอนอัพโหลด (< 5 วินาที)**: โครงสร้างไฟล์ครบไหม, เวอร์ชัน library ตรงไหม, ขนาดเกินไหม, โหลด artifact ขึ้นไหม

**Dry run (ไม่กินโควตา)** — รัน pipeline เต็มรูปแบบบน `val` แทน test แล้วคืน metric จริงให้ดู
ถ้าผ่าน dry run แล้ว โอกาสพังบน test เกือบเป็นศูนย์ เพราะเดินเส้นทางเดียวกันทุกขั้น

**ข้อความ error ต้องระบุสาเหตุที่แก้ได้** เช่น

```
❌ Schema mismatch หลัง transform()
   train มี 43 คอลัมน์ / test มี 41 คอลัมน์
   คอลัมน์ที่หายไปใน test: ['city_Nakhon', 'city_Phuket']
   สาเหตุที่พบบ่อย: ใช้ pd.get_dummies() ใน transform() โดยไม่ตรึงรายการหมวดหมู่ไว้ตอน fit()
```

## 13. ประเด็นที่ต้องตัดสินใจต่อ competition

`TaskSpec` ของแต่ละวิชาต้องประกาศให้ครบ

| # | ประเด็น | หมายเหตุ |
|---|---|---|
| 1 | คะแนนหลัก (macro-F1 / PR-AUC / ROC-AUC) | ขึ้นกับความไม่สมดุลของข้อมูล (§6.3) |
| 2 | `classes` และลำดับ | ต้องตรึงตายตัว โมเดลคืน probability ตามลำดับนี้ |
| 3 | **สัดส่วน train/val/test_public/test_private** | ผู้สอนกำหนดเอง — 60/15/10/15 เป็นแค่จุดตั้งต้น ต้องดูขนาดชุดข้อมูลจริงและตารางความละเอียดใน §1 ประกอบ พร้อมตั้ง `stratify_by` / `group_by` ให้ถูก |
| 4 | Package whitelist | เช่น อนุญาต LightGBM/XGBoost ไหม, timm ไหม |
| 5 | อนุญาต pretrained weights ไหม | ถ้าอนุญาต ต้องรวมมาในไฟล์และกระทบ quota |
| 6 | โควตาส่งต่อวัน | GPU lane ควรน้อยกว่า CPU lane |
| 7 | เพดานขนาดโมเดล | มีผลต่อ storage และเวลาในคิว |
| 8 | นับ inference cost เป็นส่วนหนึ่งของคะแนนไหม | ถ้าจะนับ **ห้ามใช้ wall-clock** — ให้ใช้จำนวนพารามิเตอร์หรือ FLOPs ที่นับได้แน่นอน ตามหลักการ hardware-independent scoring |
